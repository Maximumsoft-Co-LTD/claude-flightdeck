# Conform to the Codebase — detect conventions before imposing them

> **The rule:** a preset's architecture (hexagonal, Feature-Sliced Design,
> Pinia stores, Helm layout, …) is a **default assumption, not a mandate.**
> Before writing code, detect how *this* project actually organizes itself
> and conform to that. The codebase's reality wins over the preset's ideal.
> When they conflict and you'd have to *introduce* the preset's architecture
> into a project that doesn't use it — **STOP and ask.**

## Why this exists

The core `backend-engineer` / `frontend-engineer` carry **no architecture of
their own** — but it's still tempting to assume a familiar layout. Don't. A
Go service might be a flat `main.go` + `handlers/` + `db/` or a layered
`internal/` tree; a frontend might be plain `app/` + `components/` or a
sliced `features/entities/` layout. If the engineer applies a layout the
project never used, it produces code that's "clean" by some textbook but
wrong for *this* repo. Read first, then match.

This is the structural cousin of `programming-fundamentals.md` rule 7
("read the existing code first") — applied to **architecture**, not just to
finding a helper. The persisted answer lives in
[`../../.claude/rules/code-style.md`](../../.claude/rules/code-style.md),
generated by `/onboard`; this procedure is how an agent confirms + extends it
per task.

## The detect → conform → ask procedure

Run this BEFORE writing any code (it's part of every coding agent's
pre-task ritual):

### 1. Detect the project's actual conventions

- **Glob the area you're about to touch** and **Read 2-3 representative
  existing files** (a handler, a model, a test). How does *this* project
  name things, layer things, wire things?
- **Read `.claude/rules/code-style.md` + the area's `CLAUDE.md`** (if present)
  — the documented conventions win over your inference. The live code wins
  over both if they've drifted (note the drift).
- **Look for the project's own structural signals** — e.g. a layered
  `internal/{domain,ports,usecase}` tree or a flat `handlers/`; a sliced
  `features/entities/shared/` frontend or plain `components/`; a lint/make
  target that enforces a boundary. Whatever the project actually does is the
  pattern you follow.

### 2. Decide

| Observation | Action |
|---|---|
| The project has a clear, consistent pattern | **Conform to it.** Match its layout, naming, error handling, and test style. (If a custom preset's architecture matches, enforce its boundary tooling as normal.) |
| The project's pattern differs from what you'd assume | **The project wins.** Match its reality; do NOT introduce a parallel structure. Note any drift from `code-style.md` in your report. |
| Ambiguous/inconsistent, OR the task would force you to **introduce** a structure the project doesn't use | **STOP. Report `NEEDS_CONTEXT`** (see below). Do not impose. |

### 3. Ask (on conflict / ambiguity)

Report `NEEDS_CONTEXT` with:

- **What you observed** — the actual layout (paste the directory tree / a
  representative file path).
- **The conflict** — e.g. "the service is a flat `handlers/` + `store/`
  layout; this task's design assumes a `usecase/ports` split that doesn't
  exist here."
- **The options** — "(a) follow the existing flat layout for this task, or
  (b) introduce the layered structure for this module (larger change, should
  be its own design-doc decision)."

Then wait for the operator's choice. Introducing an architecture a project
doesn't use is an architectural decision (A005) — it belongs in a design
doc and a human call, not an unasked-for side effect of a feature task.

## What this does NOT mean

- It does **not** mean "match every local quirk forever." Genuinely bad
  local patterns can be improved — but that's a design-doc decision, raised
  explicitly, not imposed mid-task.
- It does **not** loosen TDD, the gates, or the other A-rules. Those are
  universal; only the *structural shape* yields to the codebase.
- If a **custom preset** is installed and the project genuinely follows its
  architecture, enforce it strictly — that's the preset's whole value.

## If an installed preset is wrong for the project

If detection shows a custom architecture preset doesn't fit at all, flag it:
the operator can re-run `/onboard` or re-install without that preset. The
onboarding wizard runs an
**architecture-fit** probe at setup time to catch this before dispatch —
see [`onboarding-guide.md`](onboarding-guide.md).
