# Repo / Component → Subagent Mapping

> Loaded by `/work` Step 1 when picking the `subagent_type` for the
> dispatch. The right agent reads the project's learned conventions
> (`.claude/rules/code-style.md`) and matches the codebase's real style.

## How to read this file

The template ships **architecture-agnostic** engineers in core. They do not
impose hexagonal / FSD / any fixed structure — they read
`.claude/rules/code-style.md` (generated by `/onboard`) + sample the actual
code and conform to it (see [`../../../../docs/setup/conform-to-codebase.md`](../../../../docs/setup/conform-to-codebase.md)).
Custom presets (the install-time `--preset` flag) may add their own
specialized agents; route to those when installed.

## Default mapping (core — no preset needed)

| Work class | `subagent_type` |
|---|---|
| Any server-side feature — handler/endpoint, use-case/service, data access, migration, job/worker, message producer/consumer | `backend-engineer` |
| Any client-side feature — page/route, component, client state, form, API client call, i18n | `frontend-engineer` |
| Cross-service / cross-area architectural decision | `senior-tech-lead` |
| Boundary / architectural review (Gate 3) | `senior-tech-lead` (reads the project's learned boundary conventions) |
| ≥500-line design doc authoring | `design-doc-writer` |
| Post-FE-sprint visual fidelity gate | `/review design` (skill, not agent) |

Both engineers are **convention-driven**: they place new code where the
project already puts that kind of code, name things the way the project does,
and match its error-handling + test style — then raise quality *within* that
pattern (TDD + the 6 gates). If the layout is ambiguous or the task needs a
structural decision, they STOP and report `NEEDS_CONTEXT` rather than impose.

## Preset mapping (only if a preset is installed)

| Preset | Adds | Use for |
|---|---|---|
| `k8s-helm` | `k8s-engineer` | Helm charts, Kustomize overlays, ArgoCD/Flux manifests, RBAC/NetworkPolicy, CI/CD |
| _custom (you authored)_ | _its agents_ | _per the preset's own mapping — see `docs/adding-new-preset.md`_ |

If no installed preset owns the work, use the core default mapping above.

## Built-in fallbacks

| Work class | `subagent_type` |
|---|---|
| Multi-step task that fits no engineer | `general-purpose` |
| Read-only exploration / file search | `Explore` |
| Greenfield feature design + blueprint | `feature-dev:code-architect` |
| Deep-trace an existing feature code path | `feature-dev:code-explorer` |
| Generic code review | `feature-dev:code-reviewer` |

## Reviewer mapping (Gate 3 of post-delegation review)

Gate 3 (boundary / architecture) is handled by **`senior-tech-lead`** by
default — it reads the project's learned conventions
(`.claude/rules/code-style.md` + area `CLAUDE.md`) and checks the new code
respects the **project's own** boundaries, not a prescribed architecture. A
custom preset may ship a dedicated boundary reviewer; use it when installed.

## Mixed-stack tasks

A task spanning frontend + backend (e.g. "implement X endpoint AND its UI
consumer") is split into TWO sub-tasks BEFORE dispatch:

- Sub-task A (BE) → `backend-engineer`
- Sub-task B (FE) → `frontend-engineer`

The contract change goes in a third PR that lands FIRST (see
`/work` Conflict Radar Layer 3). Never dispatch a single agent to
write both sides of a contract.

## Anti-patterns

- ❌ Dispatching `general-purpose` for a normal feature task. The engineers
  read `code-style.md` + the gates; `general-purpose` starts cold.
- ❌ Picking a reviewer agent as the implementer. Reviewers are read-only.
- ❌ Using `Explore` to write code. It's read-only — it cannot commit.
